# 性能优化结果（2026-10-16—17）

实现范围与业务约束见[实施记录](./implementation.md)，已确认的设计见[分析](./2026-10-16-analysis.md)。应用代码为 `f06e96b`，原始代码为 `7ac7921`；后续提交仅补测量脚本和文档。本轮在本机独立生产构建和专用合成数据库验证，尚未部署到实际使用环境。

## 条件和指标

- Linux ARM64，20个逻辑CPU、121.7GiB内存；Node24.16.0，PostgreSQL16，应用与数据库同机、loopback网络。默认页面100行，桌面1440×1000、Asia/Shanghai。
- 初始夹具10项目×每项目1万记录、10个独立用户，正常签名SSO会话、逐请求查库授权。重复写入负载会增加记录，每份JSON的 `rowsAtStart` 是真实起始数量，`originalRowsPerProject`/`rowsPerProject` 只是初始夹具参数。
- 主要路径验收为切换/筛选p95≤1000ms、主要页面可用≤2000ms、单条保存确认≤1000ms。采用最近秩分位数 `ceil(n×0.95)-1`；保留n/p50/p95/max，少量样本只作为探索。
- 保存从浏览器真实点击计到本次写入成功、刷新JSON成功、页面总数/编辑摘要匹配、弹窗完全卸载、无忙状态/骨架且完成两帧绘制。`observedMs` 与 `driverMs` 另存；两帧是本次刷新后的绘制证据，不能用旧结果替代。
- 基准使用专用端口3110/3111和 `budget_perf_*` 库，测试另用独立测试库。计时期间不并跑构建、测试、数据核对或其他基准。服务预热；浏览器首次页面使用独立上下文、空缓存，不涵盖进程冷启动。

## 为什么继续处理附件干扰

仅保留刷新中的表格行改善了加载反馈，没有证据证明它单独缩短保存时间；它的价值是保留内容并禁止对旧结果再次操作。

[早期驱动对照](./results/2026-10-16/edit-observer-complete.json)在同一100次修改中，驱动观察p95约1087ms，真实界面完成约801ms；[独立刷新证据复核](./results/2026-10-16/writes-observer-verified.json)又以100次新增、100次修改验证。主指标因此改为浏览器内完成时刻，保留驱动耗时。该计时校准不算代码提速，也没有改变1秒目标。

校准后仍有真实超标：[只分段读取附件](./results/2026-10-16/chunked-zip-100.json)新增p95为1079.8ms；[增加协作让行](./results/2026-10-16/priority-zip-100.json)后仍为1017.1ms。因此没有据小样本边缘通过结果停止。

进一步发现无编号的疑似查重读取了对应年度全部记录。现在先用相同金额/日期筛数据库候选，仍执行原摘要归一化指纹；各集合超500个值或格式不规范时按字段回退，不截断结果。真实PG回归的候选数从103降至1；500/501边界、混合无效格式、已有编号记录匹配均有覆盖。最终100次新增/修改的结果见上表。

## 探索与边界

[最终探索数据](./results/2026-10-16/final-explore.json)：80ms网络延迟、5Mbps下载/1Mbps上传，每项3样本；项目记录页p95 1648.7ms，台账1046.0ms，筛选585.8ms。弱网络不属于本轮主验收，3样本不能证明稳定分位。

2000行预览351.4ms，2360个DOM节点、每页100行，跨页选择保持。1/8/50MiB随机附件各一次上传约75.1ms, 262.3ms, 1782.7ms，下载字节SHA256一致；附件上传另计，不计入单条记录保存确认。

[200/1000/2000行规模探索](./results/2026-10-16/final-import-sizes.json)各一次，解析/预览/确认与真实新增数检查均通过：

| 行数 | 解析(ms) | 预览API(ms) | 确认(ms) |
| ---- | -------: | ----------: | -------: |
| 200  |     69.5 |        13.1 |     72.0 |
| 1000 |    167.3 |        28.0 |    314.9 |
| 2000 |    246.7 |        37.4 |    551.0 |

当前大Excel和大ZIP共用一个进程内名额，最多8个等候、30秒超时，出队重新授权；小任务直接执行。ZIP捕获成员后按元数据大小拆成不超过8MiB的读取段，单个更大附件独占一段。每段等待40ms日常API安静窗口，最多让行1秒；无法抢占已经开始的读取。任务区间重叠包含排队与让行时间，表示用户有重任务进行中，不等于每刻都在占CPU。

Excel保留ID清单和压缩输出，ZIP仍物化整批二进制；RSS含V8保留堆、原生缓冲和运行历史。它们均不是常量内存实现。此前五万条级文档式导出曾出现约3.31GB RSS和2秒以上交互；改为流式写入、分批读取并限制并发后显著改善，但[改前](./results/2026-10-16/large-before.json)/[早期流式](./results/2026-10-16/large-after-stream.json)运行的数据和进程历史不同，只作为调查证据。

实际部署硬件/网络、长期稳态、进程冷启动、横向多实例预算、多个大附件并发上传及完整512MiB ZIP上限载荷仍需上线环境复测；本轮验证了容量拒绝逻辑，真实打包载荷为24MiB，不外推到512MiB。大附件如果在部署环境持续影响目标，再设计独立执行进程/持久任务或存储迁移。跨请求身份缓存、财务预计算和严格导出快照未引入。
