# 机器认证采用服务账号 + 静态 API Key

coding agent 需要无人值守地操作预算系统(定时导入结算单、维护记录等),而系统原有认证只有人类会话(Authentik OIDC cookie / mock header)。我们决定:为 agent 建真实 `User` 服务账号(与人类同受角色与项目成员权限矩阵约束),认证用静态 API Key(`bma_` 前缀,SHA-256 入库、仅创建时展示一次、可撤销,`Authorization: Bearer`);`unattended` 凭证在服务端直接拒绝硬排除动作(作废/审批/成员管理,见 `permissions.ts`)。

## Amendment(个人凭证 + 针对性权限)

随后扩展为两类凭证,机制完全共用:

- **个人凭证**:任意用户在「API 凭证」页自助签发/撤销,绑定本人身份(审计归真、授权免维护,类似 GitHub PAT)。凭证管理接口拒绝一切 Bearer 调用——防 agent 自我签发凭证。
- **scope 只收窄不放大**:实际权限 = 用户权限 ∩ 凭证范围。凭证带档位(只读/读写/完整)、项目范围(全部/指定)、可选有效期;创建后不可编辑,要改就撤销重发。拦截统一收口在 `requirePermission`(全部读写路径——含读——已在 service 层收口于此),命中写审计 `apikey.denied`。
- **服务账号保留**:长期无人值守定时任务的凭证不应绑定个人身份(人员变动不使定时任务失效),`make-agent` 场景继续存在。

## Considered Options

- **长效 JWT**:无人值守要处理过期与刷新,复杂度白付;静态 key 可即时撤销,更适合机器。
- **agent 模拟浏览器走 SSO**:脆弱,依赖 Authentik 页面流程不变。
- **策略仅文档约束(不做服务端拦截)**:被提示词注入或失控的 agent 仍能执行不可逆操作;拦截成本极低而收益是系统级兜底。
- **仅服务账号、不做个人自助凭证**:每次都要管理员维护影子账号的成员关系,且审计里操作人不是真实用户;个人凭证 + scope 收窄后泄露爆炸半径也可控。

## Consequences

- 服务账号的权限收放完全复用现有成员管理(移出 OWNER 即收权),零新权限代码;个人凭证的权限自动跟随本人成员关系变化。
- 在场交互若需执行硬排除动作,使用 attended 凭证(`make-agent --attended` 或「API 凭证」页选「在场交互」)。
- key 泄露的影响范围 = 所属用户权限 ∩ 凭证范围(档位/项目/模式/有效期四层收窄);撤销后 agent 立即 401。
- 读路径的 scope 收窄依赖 service 层统一的 `requirePermission('project:view')` 调用——新增读接口必须走 service 层检查,不得在路由层裸放行。
