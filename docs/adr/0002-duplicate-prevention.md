# Excel 导入与录入的重复数据防护:docNo 硬重复 + 指纹疑似 + 部分唯一索引

业务记录的重复入账直接污染台账(重复金额、虚增占用),而写入口众多——标准模板导入、结算单导入、手动新增/编辑、coding agent(MCP)。我们决定:抽统一查重判定器供全部写入口共用;**docNo(财务系统单据编号)在项目内命中未作废记录 = 硬重复,禁止入账且无强制通道**;无编号行走**查重指纹**(年度+金额+业务日期+摘要归一化)命中 = 疑似重复,提示后允许人工强制;数据库加部分唯一索引 `(project_id, docNo) WHERE docNo IS NOT NULL AND is_void = false` 作并发与旁路的最终兜底。

## Considered Options

- **只靠预览标注「疑似重复」(旧行为)**:docNo 命中也能人工强制,真重复照样入库;且手动/MCP 入口完全无查重。
- **指纹命中也一律禁止**:同日同额同摘要的两笔真实支出并不罕见,一刀切会逼用户改摘要绕过,数据更脏。
- **唯一索引不含 is_void 条件**:作废后无法重导同一单据(重导是合法流程),故 partial index 只约束未作废记录——「作废即释放编号」。

## Consequences

- 硬重复无任何人工覆盖后门;误判的唯一出路是作废旧记录或改号,语义清晰。
- 指纹刻意不含科目(结算单导入时科目后填)且摘要只做空白归一化不做模糊匹配——误报可控,人工强制才有效。
- 部分唯一索引 Prisma schema 无法表达,以裸 SQL 迁移维护;导入行 `duplicate_level` 区分 hard/suspected,旧行 duplicateFlag=true 按 suspected 对待(保持历史可强制行为)。
- 新增业务记录写入口必须接入 `duplicateCheck.service`,否则唯一索引虽能兜底 docNo,指纹疑似提示与可读错误(409/422 而非裸 P2002)会缺失。
